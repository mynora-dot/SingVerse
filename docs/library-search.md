# 媒体来源与歌曲列表查询

媒体库管理和歌曲管理统一采用上方搜索表单、下方数据表格。搜索条件点击“查询”后提交，修改未提交的输入不会影响刷新/分页；“重置”清空条件并回到第一页。每页可选 20、50、100 条，显示总数、页码并支持跳页，切换页大小回到第一页。歌曲筛选及页大小保存在路由 query 中。

媒体来源支持名称或目录地址包含搜索、来源类型精确筛选、解析方案精确筛选。歌曲支持来源、文件名包含搜索及解析复核状态；复核状态仍是文件名解析状态，不是刮削审核状态。所有筛选在数据库分页前执行，返回过滤后的总数；百分号、下划线按普通字符处理。

`GET /api/v1/media-sources` 增加可选 `q`、`type=LOCAL|WEBDAV`、`profileId`，保留原 page/size 默认值和响应结构。歌曲接口仍使用现有契约，size 可在 1～100 之间。业务查询及计数都在 模块内嵌 SQL，值通过命名参数绑定；来源查询在只读事务中完成列表及计数。

## 深分页与索引

分页采用延迟关联：内层按条件及稳定排序只选当前页 ID 与排序键，外层才读取来源字段、完整歌曲解析 JSON 及确认元数据。避免在偏移过程中为每条跳过记录加载大字段或关联元数据。排序分别是来源 `created_at DESC,id ASC`、歌曲 `scanned_at DESC,id ASC`；相同时间戳通过 ID 保持顺序。

SQLite/MySQL 的 `202611070001_initial_schema.sql` 直接定义排序联合索引：歌曲全局时间、来源+时间、复核状态+时间、来源+复核状态+时间；来源全局时间、类型+时间、解析方案+时间。ID 是每个排序索引的最后一列。来源歌曲索引供单来源扫描索引接口及清理使用。

这种分页保留后台常见的任意跳页，但 OFFSET 仍需要走过前面的索引项，不是常数时间的游标翻页。SQLite 查询计划测试验证深偏移的常用精确筛选使用覆盖索引且无需临时排序；不将此描述为任意数据规模下的性能保证。多条件组合由数据库优化器选择索引，并非所有组合都有单独索引。

`%关键词%` 包含搜索以及 LOWER 处理不能靠普通 B-tree 索引消除扫描，因此没有为名称/地址/文件名添加无效的“包含搜索索引”。大库先选择来源、类型或状态缩小范围；当前没有引入全文搜索引擎。后续如需百万级交互式顺序浏览，应使用游标 API 或专门的搜索索引，而非无限增加 OFFSET。

本次不修改扫描规则、刮削数据和原始媒体文件。接口行为、分页、索引计划通过隔离数据库测试，不代表真实 NAS/MySQL 性能压测。


歌曲位置页面现已改为少量来源卡片，不再提供来源筛选栏和页码；每次加载 100 个，更多来源通过“显示更多位置”继续加载。本文来源筛选参数仍适用于 API；歌曲列表筛选与分页不变。
